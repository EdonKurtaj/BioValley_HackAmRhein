# Basel logistics dashboard

Administrative logistics staff need to see environmental disturbances and refrigerated shipments approaching a production deadline. The dashboard combines a Basel MapLibre map, regional measurement cards, an incident panel, a shipment list and selectable shipment details.

## Demo flow

Start playing in clearly labelled Demo mode. Select a truck to see its route, moving simulated position, departure, ETA, destination, package temperature/history, distance and production need-by time. Inspect the full weighted score and its explanation. Replay normal operation, traffic delay, an urgent shipment, a suitable alternative route, a temperature excursion, or the single-truck extreme-conditions case. The latter combines a simulated package excursion, a 45-minute route disruption and a short need-by window; it demonstrates the high combined demo index and why quality review overrides dispatch advice. Pause or resume the accelerated replay; restarting or choosing a scenario starts playback automatically, and Play restarts a finished replay. Quality review takes precedence over transport advice; a synthetic hold freezes the affected truck on its current road, including after a reroute, while temperature monitoring continues and its ETA is labelled planning-only.

Switch to Live mode to retrieve saved environmental observations from Supabase through the backend. Show measurement timestamps and stale/missing inputs. Regional traffic messages are candidates for route review. No live shipment feed exists yet, so Live mode has an explicit empty shipment state. A failed live request remains an error and never substitutes demo evidence.

## Architecture

`frontend/` is an independent Vite React application. The existing Python collection code and Supabase schema remain separately runnable. UI components consume the validated dashboard response; they never access the database or ingestion files directly. The shared contract lives in [interfaces.ts](../frontend/src/interfaces.ts).

The local Python HTTP server reuses the existing thermal exposure, priority and decision functions and implements GET /api/dashboard. It starts the existing collector for periodic source refresh while it runs. Demo replay inputs live in config/demo-transports.json. Road geometry comes from a committed cache of full OSRM driving routes over OpenStreetMap, rendered through MapLibre GL Directions. OSRM performs the road-graph search; the backend ranks its candidates by travel-time cost, rejects a synthetic closed directed segment, and requires a shared travelled prefix. In the reroute scenario the backend policy first recommends an alternative, then the replay applies it after five simulated minutes, preserving the current road position and updating ETA, slack and distance. The BV-104 reroute scenario and persistent card/map/detail labels identify the affected truck; a map button focuses the divergent streets, since the paths share an initial corridor. Keep the simulated closure visible after the switch as an avoided incident and show its original delay as the trigger; active-route counts and scoring exclude the avoided section. An unsuitable/missing alternative keeps the original path. Marker animation interpolates along the supplied streets; it does not calculate risk. The server also serves the built frontend. Vite proxies /api to the server in development. Database credentials stay on the server.

## Out of scope

Real GPS, package sensors, validated product stability rules, automatic dispatch, authentication and qualified routing are outside this demo. Road geometry is based on cached OpenStreetMap routes; transport identities, delays, temperatures, GPS positions and timing in Demo mode are synthetic. Candidate selection covers the returned OSRM alternatives, not every possible path or a guaranteed global second-shortest route. The public driving profile is not live-traffic-aware and does not validate heavy-truck, hazardous-material or cold-chain suitability. Route distances follow the road geometry; timing retains the authored accelerated demo schedule. OpenStreetMap tiles require internet access. Demo evidence coverage describes completeness of synthetic inputs, not scientific validation.
